# DNS `ndots` demo

> **_NOTE_**: This doc and demo was prepared with AIL:3. I described the whole
> story and the journey. AI created and tested.
> [AI Influence Level](https://danielmiessler.com/blog/ai-influence-level-ail)

This demo compares Kubernetes' default DNS configuration with KubeDNS Shepherd
and native `MutatingAdmissionPolicy` using three common lookups:

| Use case | Application lookup | Endpoint |
| --- | --- | --- |
| Same namespace | `api` | A real `api` Service in the caller's namespace |
| Other namespace | `api.prod` | A real `api` Service in the `prod` namespace |
| Outside cluster | `api.prod.external.test` | A record served by the demo CoreDNS instance |

The cluster domain is `example.test`. The baseline uses Kubernetes' default
resolver configuration:

```text
search default.svc.example.test svc.example.test example.test
nameserver 10.96.0.53
options ndots:5
```

The two optimized cases use `ndots:2`, `edns0`, and put
`svc.example.test` first. The DNSClass configuration is in
[`helm-values.yaml`](helm-values.yaml), and the native alternative is in
[`../examples/mutating-admission-policy.yaml`](../examples/mutating-admission-policy.yaml).

## Run

You need Kind, `kubectl`, Helm, and Docker, Podman, or nerdctl. From the
repository root:

```sh
./docs/dns-demo/setup.sh
./docs/dns-demo/measure.sh
```

Use `QUERIES` to change the default 250 application lookups per row:

```sh
QUERIES=1000 ./docs/dns-demo/measure.sh
```

## Actual results

These results were produced by `measure.sh` with 250 successful application
lookups in every row:

```text
Target                  Use case          Scenario              ndots   App lookups Client DNS req    NXDOMAIN
api                     same-namespace    baseline                  5           250            250           0
api                     same-namespace    kubedns-shepherd          2           250            500         250
api                     same-namespace    native-policy             2           250            500         250
api.prod                other-namespace   baseline                  5           250            500         250
api.prod                other-namespace   kubedns-shepherd          2           250            250           0
api.prod                other-namespace   native-policy             2           250            250           0
api.prod.external.test  outside-cluster   baseline                  5           250           1000         750
api.prod.external.test  outside-cluster   kubedns-shepherd          2           250            250           0
api.prod.external.test  outside-cluster   native-policy             2           250            250           0
```

The result depends on both `ndots` and search-domain order:

- Same namespace: the optimized configuration sends 100% more DNS requests
  because it tries `api.svc.example.test` before the namespace-specific name.
- Other namespace: the optimized configuration sends 50% fewer requests.
- Outside cluster: the optimized configuration sends 75% fewer requests.

## How measurement works

The load generator still uses Go's standard resolver. It only wraps the
resolver's network connection to observe the DNS packets already generated by
Go. It does not create candidate names or implement custom resolution logic.

The application output includes every candidate name and response code. An
intermediate `NXDOMAIN` is counted even when a later candidate succeeds, which
is why application failures can be zero while the NXDOMAIN count is non-zero.

The script does not use server-side logs or metrics. For real-cluster
monitoring, CoreDNS exposes useful counters such as
`coredns_dns_requests_total` and
`coredns_dns_responses_total{rcode="NXDOMAIN"}`.
