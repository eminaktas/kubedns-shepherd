# Understanding Kubernetes DNS query amplification

> **_NOTE_**: This doc was prepared with AIL:3. I described the whole story and the journey. AI created
full text. [AI Influence Level AIL](https://danielmiessler.com/blog/ai-influence-level-ail).

Kubernetes makes service discovery convenient by giving Pods a search list and,
commonly, `options ndots:5` in `/etc/resolv.conf`. At scale, that convenience can
turn one application lookup into several DNS requests. Most of the additional
requests ask for names that do not exist, increasing load and latency in the
cluster DNS path and, depending on the DNS topology and search domains, in
upstream resolvers as well.

KubeDNS Shepherd exists to make this behavior a cluster policy instead of
requiring every application owner to understand and configure resolver details.

## Why this project exists

The behavior first became visible to me while working at Trendyol.
`ndots:5` was causing applications to try unnecessary search-expanded
names. Those failed lookups added traffic to the cluster DNS service and, in the
DNS topology in use there, to upstream DNS infrastructure. The cost of one
lookup was easy to ignore; the aggregate cost across many replicas, connections,
retries, and applications was not.

The issue had been discussed in the Kubernetes community for years, but there
was no cluster-level kubelet setting that could safely change the default for
all Pods. I proposed such a capability in Kubernetes issue [#116117](https://github.com/kubernetes/kubernetes/issues/116117).
I worked the issue with a colleague when I was at Trendyol and he published a [Kyverno policy](https://kyverno.io/policies/other/dns-policy-and-dns-config/dns-policy-and-dns-config/) that centrally configures Pod DNS. KubeDNS Shepherd was created to provide that capability without requiring each workload manifest to carry its own DNS configuration.

Kubernetes later introduced `MutatingAdmissionPolicy`, making a built-in,
declarative solution possible on newer clusters. An early DNS example was shared
in [kubernetes/kubernetes#127137](https://github.com/kubernetes/kubernetes/issues/127137#issuecomment-2603247342).
KubeDNS Shepherd remains useful when broader Kubernetes compatibility, dynamic
cluster DNS discovery, templated search domains, or a reusable `DNSClass` API is
needed.

## How `ndots` changes a lookup

A typical Pod receives a resolver configuration similar to this:

```text
nameserver 10.96.0.10
search payments.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

`ndots` is the number of dots a name must contain before the resolver tries it
as an absolute name first. A trailing dot always makes a name absolute.

Consider an application looking up `api.prod.example.test`, which contains
three dots. With `ndots:5`, it is below the threshold, so the resolver tries the
search list first:

```text
api.prod.example.test.payments.svc.cluster.local.  -> NXDOMAIN
api.prod.example.test.svc.cluster.local.           -> NXDOMAIN
api.prod.example.test.cluster.local.               -> NXDOMAIN
api.prod.example.test.                             -> success
```

With `ndots:2`, the same name is tried as absolute first and succeeds with one
request. Writing `api.prod.example.test.` with a trailing dot has the same
absolute-first effect regardless of `ndots`.

The exact amplification is resolver- and workload-dependent. A lookup may
produce both A and AAAA requests, a Pod may have more search domains, and retries
can multiply the result again. Caching and connection reuse can reduce it. The
important relationship is:

```text
application lookups
  x candidate names generated by the search list
  x record types (often A and AAAA)
  x retries
  = DNS requests seen by the DNS path
```

CoreDNS normally answers names under the cluster domain itself. Other search
suffixes and the final external name can be forwarded upstream. Consequently,
the exact split between cluster-local and upstream load depends on the CoreDNS,
kube-dns, NodeLocal DNSCache, and corporate DNS configuration. Even when the
failed candidates never leave CoreDNS, they still consume cluster DNS CPU,
network, queue, cache, and latency budget.

Marco Pracucci's article,
[Kubernetes pods `/etc/resolv.conf` `ndots:5` option and why it may negatively affect your application performances](https://pracucci.com/kubernetes-dns-resolution-ndots-options-and-why-it-may-affect-application-performances.html),
provides a detailed production example and before/after graphs.

## Why `ndots:2` is a common compromise

`ndots:2` keeps convenient names such as `service` and `service.namespace`
search-relative, while names with two or more dots are attempted as absolute
first. That is often a useful balance, but it is not universally correct. Test
the applications and naming conventions in your cluster before enforcing it.

Lowering `ndots` is one part of DNS capacity management. Also consider:

- using absolute names with a trailing dot for known external endpoints;
- reusing connections instead of resolving for every request;
- enabling and sizing NodeLocal DNSCache where appropriate;
- monitoring request rate, NXDOMAIN responses, latency, throttling, and timeouts;
- reviewing non-cluster search domains that can send failed candidates upstream.

## Applying the policy with KubeDNS Shepherd

The Helm chart can deploy a `DNSClass`. The following values target
selected namespaces, change matching Pods to `dnsPolicy: None`, and supply a
complete resolver configuration. If `nameservers` is omitted, KubeDNS Shepherd
can discover the cluster DNS service from kubelet configuration. Search entries
can use `.podNamespace` and `.clusterDomain` templates.

```yaml
dnsclass:
  allowedNamespaces:
    - payments
    - checkout
  disabledNamespaces:
    - kube-system
  allowedDNSPolicies:
    - ClusterFirst
    - ClusterFirstWithHostNet
    - None
  dnsPolicy: None
  dnsConfig:
    searches:
      - "svc.{{ .clusterDomain }}"
      - "{{ .podNamespace }}.svc.{{ .clusterDomain }}"
    options:
      - name: ndots
        value: "2"
      - name: edns0
```

Enable the DNSClass while installing or upgrading the chart:

```sh
helm upgrade --install kubedns-shepherd \
  kubedns-shepherd/kubedns-shepherd \
  --namespace kubedns-shepherd-system \
  --create-namespace \
  --set dnsclass.enable=true \
  --values values.yaml
```

New and recreated Pods in the selected namespaces are mutated. Existing Pods do
not change in place because their DNS configuration is effectively immutable;
restart or roll out the owning workload after introducing or changing a policy.
Verify the result on an admitted Pod:

```sh
kubectl exec -n payments <pod-name> -- cat /etc/resolv.conf
kubectl get pod -n payments <pod-name> \
  -o jsonpath='{.metadata.annotations.kubedns-shepherd\.io/dns-class-name}{"\n"}'
```

Start with an allowlisted namespace, observe DNS and application metrics, and
then expand the scope. Avoid defining overlapping `DNSClass` resources: a Pod
must have one unambiguous cluster DNS policy.

## Native Kubernetes alternative

[`MutatingAdmissionPolicy`](https://kubernetes.io/docs/reference/access-authn-authz/mutating-admission-policy/)
is a built-in, CEL-based alternative to a mutating webhook. It is stable and
enabled by default in Kubernetes 1.36. Kubernetes 1.34 and 1.35 provide a beta
API that must be explicitly enabled; older alpha releases require additional
care and use a different API version. Check the exact feature gates and runtime
API configuration for your Kubernetes distribution.

The example in
[`docs/examples/mutating-admission-policy.yaml`](examples/mutating-admission-policy.yaml)
uses the stable `admissionregistration.k8s.io/v1` API. It selects Pods through
an opt-in label. Like the Kyverno example, it changes a supported DNS policy to
`None` and supplies a nameserver, search domains, `ndots:2`, and `edns0`:

```yaml
spec:
  template:
    metadata:
      labels:
        kubedns-shepherd.io/dns-ndots-policy: enabled
```

Apply the policy and binding before creating the workload:

```sh
kubectl apply -f docs/examples/mutating-admission-policy.yaml
```

The example contains concrete values for the reproducible demo. Change its
nameserver and domains to match the target cluster before using it elsewhere.
The mutation replaces the selected Pod's resolver configuration. If the cluster
requirement must be mandatory, pair mutation with validation so a later
admission step rejects disallowed values. Admission policies run only when an
object is admitted; they do not rewrite existing Pods.

## Choosing an implementation

| Approach | Best fit | Important trade-off |
| --- | --- | --- |
| Trailing-dot FQDN or per-Pod `dnsConfig` | A few known applications or endpoints | Simple and precise, but relies on every workload owner |
| KubeDNS Shepherd | Central policy, dynamic DNS discovery, templated search domains, or older clusters | Runs a controller and admission webhook |
| Native `MutatingAdmissionPolicy` | Kubernetes 1.36+ clusters needing a small declarative mutation | Version-dependent API; complex discovery or configuration needs additional resources and CEL |
| Kyverno | Clusters already using Kyverno for policy management | Adds or depends on the Kyverno policy engine |

Do not run multiple mechanisms over the same Pods unless their ownership and
ordering are deliberately designed. Competing mutators can produce surprising
results or admission conflicts.

## Reproduce the effect

The [`docs/dns-demo`](dns-demo/README.md) environment tests a Service in the
caller's namespace, a Service in another namespace, and an endpoint outside the
cluster. It compares Kubernetes' default resolver configuration with KubeDNS
Shepherd and native `MutatingAdmissionPolicy`.

The load generator uses Go's standard resolver and observes the DNS packets it
produces. It does not implement DNS search or fallback logic. The measured
results for 250 successful lookups were:

| Use case | Lookup | Baseline requests / NXDOMAIN | Optimized requests / NXDOMAIN | Change |
| --- | --- | ---: | ---: | ---: |
| Same namespace | `api` | 250 / 0 | 500 / 250 | 100% more |
| Other namespace | `api.prod` | 500 / 250 | 250 / 0 | 50% fewer |
| Outside cluster | `api.prod.external.test` | 1,000 / 750 | 250 / 0 | 75% fewer |

The same-namespace result shows that search-list order matters too: this policy
puts `svc.example.test` before the caller's namespace. The full per-policy
results and commands are in the demo guide.

The demo does not calculate results from CoreDNS. In a real cluster,
`coredns_dns_requests_total` and
`coredns_dns_responses_total{rcode="NXDOMAIN"}` are useful server-side metrics.
